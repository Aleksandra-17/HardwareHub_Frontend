# HardwareHub Frontend

Веб-приложение для учёта техники: устройства, типы устройств, локации, ответственные лица, отчёты и инвентаризация. Работает вместе с репозиторием **HardwareHub-Backend**.

## Стек

- **Vite** — сборка и dev-сервер
- **React 18** + **TypeScript**
- **shadcn/ui** + **Tailwind CSS**
- **React Query**
- **Vitest** + **Testing Library**

---

## Что понадобится локально

- **Node.js 20+** и **npm** (или совместимый менеджер пакетов)
- для полноценной работы с живыми данными — запущенный **HardwareHub Backend** (см. README бэкенд-репозитория), по умолчанию доступен как `http://localhost:8000`

```bash
git clone https://github.com/<ваш-орг>/HardwareHub-Frontend.git
```

## Переменная `VITE_API_URL` (связь с API)

Фронтенд обращается к API по базовому URL из переменной **`VITE_API_URL`**. Если она не задана, используется значение по умолчанию **`http://localhost:8000/api`** (см. `src/lib/api.ts`).

Все пути в коде относительные (`/auth/login`, `/devices`, …), поэтому в `VITE_API_URL` должен быть **именно префикс до `/api` включительно**, например:

- локально с бэкендом на порту 8000: `http://localhost:8000/api`
- продакшен с API на поддомене: `https://api.example.com/api`
- продакшен с одним доменом и прокси (см. раздел про сервер): `https://example.com/api`

**Локально через файл окружения Vite** (файл `.env` или `.env.local` в корне фронтенда — его вы создаёте у себя, в репозиторий обычно не коммитят):

```env
VITE_API_URL=http://localhost:8000/api
```

После изменения переменных с префиксом `VITE_` перезапустите `npm run dev` или пересоберите production-сборку.

## Локальный запуск (разработка)

```bash
npm run dev
```

- Dev-сервер Vite слушает порт **8080** и хост `::` (доступен и с localhost, и по IP в сети).
- Откройте в браузере: **http://localhost:8080**

Проверка здоровья бэкенда с машины разработчика (если API поднят):

```bash
curl -s http://localhost:8000/api/root/health
```

## Production-сборка локально

Перед сборкой задайте URL API так, как он будет доступен **из браузера пользователя** (не «внутри Docker-сети», а публичный или корпоративный адрес):

```bash
export VITE_API_URL=https://api.ваш-домен.ru/api
npm run build
```

Результат в каталоге `dist/`. Это статические файлы — их можно отдавать любым HTTP-сервером (nginx, CDN, объектное хранилище с CDN и т.д.).

Раздача через встроенный превью Vite только для проверки:

```bash
npm run preview
```

По умолчанию превью слушает **4173** — уточните в выводе команды.

## Docker (фронтенд)

Образ собирает статику через `npm run build` и отдаёт её **nginx** внутри контейнера на порту 80.

```bash
npm run docker:build
npm run docker:run
```

Сайт: **http://localhost:8080** (проброс 8080:80 как в скрипте `docker:run`).

**Важно:** в Vite значения `VITE_*` попадают в бандл **на этапе `npm run build`** внутри образа. Текущий `docker/Dockerfile` при сборке не задаёт `VITE_API_URL`, поэтому в образе останется **значение по умолчанию из кода** (`http://localhost:8000/api`). Для продакшена с другим API используйте один из вариантов:

1. Собрать статику на CI/локально с нужным URL и положить `dist/` в образ (отдельный Dockerfile или стадия `COPY dist`).
2. Добавить в `Dockerfile` перед `npm run build` строки вида `ARG VITE_API_URL` / `ENV VITE_API_URL=...` и передавать значение при `docker build` (отдельная правка репозитория).
3. Отдавать фронт с тем же хостом, что и API по пути `/api`, и оставить относительный базовый URL — тогда потребуется небольшое изменение клиента (сейчас базовый URL задаётся явно).

Переменные на `docker run` для уже собранной статики **не** подменят адрес API.

## Развёртывание на сервере и связка с бэкендом

Ниже — типовая схема без правки файлов конфигурации в репозиториях: вы настраиваете сервер, DNS и секреты у себя.

### 1. Общая идея

- Браузер загружает **статический фронтенд** (HTML/JS/CSS).
- Запросы к API идут на базовый URL из **`VITE_API_URL`** (после сборки это зашито в бандл).
- Бэкенд (FastAPI) должен отвечать по путям вида **`/api/...`** и разрешать CORS для origin фронтенда (в текущей реализации бэкенда CORS допускает широкий набор настроек; для продакшена обычно сужают список origin на стороне приложения или nginx).

### 2. Вариант A — два имени (рекомендуется)

- **`https://app.example.com`** — только фронтенд (`dist/` или Docker-nginx фронта).
- **`https://api.example.com`** — бэкенд: либо прямо uvicorn (порт 8000 за reverse proxy), либо стек из **HardwareHub-Backend** с nginx на 80/443.

Тогда при сборке фронтенда:

```bash
export VITE_API_URL=https://api.example.com/api
npm run build
```

Убедитесь, что с машины пользователя `https://api.example.com/api/root/health` отвечает 200.

### 3. Вариант B — один домен

Например, **`https://example.com`** — фронт, **`https://example.com/api/`** — проксирование на FastAPI.

Тогда:

```bash
export VITE_API_URL=https://example.com/api
npm run build
```

На nginx (концептуально): `location /api/` → `proxy_pass` на внутренний хост с FastAPI (`http://127.0.0.1:8000` или имя контейнера), с заголовками `Host`, `X-Forwarded-For`, `X-Forwarded-Proto`. Конфиг в репозитории бэкенда уже содержит пример прокси для API — при одном домене фронт и API часто объединяют **одним** корневым nginx, который отдаёт статику и проксирует `/api`.

### 4. Порядок действий на сервере (чек-лист)

1. Установить Docker (или Runtime для Node/Python + nginx) по выбранной стратегии.
2. Поднять **HardwareHub Backend** по его README (PostgreSQL, Redis, миграции, переменные окружения — как задокументировано там).
3. Проверить `GET .../api/root/health`.
4. Собрать фронтенд с **правильным** `VITE_API_URL`.
5. Выложить `dist/` или запустить Docker-образ фронта.
6. Настроить TLS (Let’s Encrypt и т.д.) на публичном nginx.
7. Открыть в firewall только **80/443** (и при необходимости SSH); порты БД наружу не публиковать.

### 5. Аутентификация и CORS

- Логин использует `POST /api/auth/login`, токен хранится в `localStorage` и передаётся как `Authorization: Bearer ...` (см. `src/lib/api.ts`).
- Если фронт и API на **разных доменах**, нужны корректные CORS и (при cookie) настройки credentials; при текущей схеме с Bearer в заголовке обычно достаточно разрешённых origin и методов на бэкенде.
